审查结论 Core Verdict

项目当前性能是否已经是最优？答：远非最优 (Far From Optimal)

虽然近期项目已升级至 Go 1.25，并在 xun/query.Get 中移除了 SELECT 的 Prepare，但在深层架构设计中，系统依然存在破坏性性能制约： 包括 V8 Context 每次调用粗暴销毁重建（引发 P99 抖动与 Runner 淘汰）、跨 CGO 仍旧依赖 4 次 JSON 文本编解码、写操作（INSERT/UPDATE/DELETE）仍承受 3x RTT、执行链路 Context 无法穿透至数据库、以及资产引擎单协程串行加载。

Architecture Vocabulary

严格遵循的架构设计词汇表 (Ousterhout 软件设计哲学)

识别浅模块与构建深模块 · 消除抽象泄露与多余消耗
Deep Module (深模块)
极简接口隐蔽极大实现复杂度，提供极高的开发与运行杠杆。
Shallow Module (浅模块)
接口复杂度接近其实现本身，不仅没减轻心智负荷，反倒增加抽象层次与内存流转开销。
Seam (接缝)
无需篡改内部即可改变、观测或取消行为的契约点。接口即测试表面。
Locality (局部性)
因相同原因变化、共享生命周期的状态与代码集中在一处，杜绝跨层泄露。
Deletion Test (删除检验)
删除该模块是聚拢了复杂度还是转移了复杂度？若聚拢则证明原设计浅薄。
Leverage (杠杆率)
接口提供的威力对比调用它所需付出的认知与集成成本之比。
Adapter (适配器)
连接两个异构接口的转换器。“一个适配器是假设接缝，两个才是真实接缝”。

Deepening Opportunities

架构摩擦点与模块深化方案 (5 大核心候选)

01

V8 执行环境纳秒级重置与上下文复用池 (Context Scope Recycler & Zero-Churn Runner)

gou/runtime/v8/runner.go · gou/runtime/v8/dispatcher.go · v8go/context.go

Strong (强烈推荐)

Problem (浅模块缺陷与高频淘汰震荡)

Runner 在隔离性设计上是一个典型的浅模块 (shallow module)： 在 runner.reset() 中，每次脚本执行完毕，直接调用： ctx.Close() 并紧接着 v8go.NewContext(iso, tmpl)。 频繁创建 Context 导致 V8 堆上的 NumberOfNativeContexts 持续上涨，触发了代码中的权宜检测： if stat.NumberOfNativeContexts > 200 { return false /* 销毁整个 Runner */ }。 在高并发场景下，Runner 实例被频繁自毁与重启，引发强烈的 **P99 延迟毛刺、Goroutine 调度抖动与 CPU 尖刺**。 此外，每次执行重新分配 console 并打印全量 Debug 日志，严重阻塞请求热路径。

删除检验 (Deletion Test)：删除 runner.reset 中的 ctx.Close() + NewContext()，状态清理的复杂度不会溢出到上层业务，而是内聚在单一的持久上下文句柄清理逻辑中，彻底消灭浅层包装。

Solution (深化为深模块)

将 Context 生命周期深化为 Context Scope Recycler（深模块）： Runner 在生命周期内常驻单一 Context。执行完毕后，仅重置挂载在 Global 上的请求级变量（`__yao_data` 等），并调用底层新增的 ctx.ResetRetainedValues() 释放单次执行持有的 Handle 引用，实现纳秒级环境复用。 彻底移除 NumberOfNativeContexts > 200 销毁 Runner 的权宜代码；将 console 作为模板单例预热，并消除热路径上繁复的日志输出。

Benefits (杠杆率、局部性与测试)

  • Leverage (杠杆率)：Runner 租借与重置延迟从毫秒级降至微秒/纳秒级，TS 业务接口 QPS 吞吐提升 3~5 倍，消除周期性延迟毛刺；
  • Locality (局部性)：隔离状态的重置收敛于 Recycler 接缝，Dispatcher 与调用方仅获得高内聚的“永远就绪”实例；
  • Testability (测试性)：直接针对 Context 复用编写 100,000 次循环压测，验证 NativeContexts 始终稳定为 1 且堆内存无泄露。

02

跨 CGO 二进制结构化克隆与零拷贝桥接器 (Zero-Copy Binary Value Codec)

gou/runtime/v8/bridge/bridge.go · gou/runtime/v8/functions/process/process.go · v8go/codec.go

Strong (强烈推荐)

Problem (浅适配器与 4x JSON 序列化瓶颈)

当前 bridge 模块是一个极度浅薄的适配器 (shallow adapter)： 虽然底层 v8go/codec.go 已实现了基于 V8 原生二进制序列化的 ValueSerializer 与 DeserializeValue， 但在 bridge.go 中，Go 传给 JS 复杂对象时仍然调用： jsoniter.Marshal(value) -> v8go.JSONParseBytes(ctx, data)； JS 返回 Go 对象时依然调用： value.MarshalJSON() -> jsoniter.Unmarshal(data, ptr)。 在业务脚本高频调用 Process("models.order.Get") 获取列表时，每次数据传输均承受 4 次全量 JSON 编解码与巨量堆内存分配，GC 压力巨大。

Solution (深化为深模块)

深化 bridge 为 Binary Value Codec（深模块）： 彻底废弃中间文本 JSON 序列化通道，全面打通基于 HTML 结构化克隆（Structured Clone）二进制格式的直传接缝； 针对字典与对象切片，利用底层高效二进制缓冲区直传映射为 V8 原生对象；对于字节流（二进制数据、加密哈希、文件缓冲区），全面对接 NewUint8Array 零拷贝内存视图。

Benefits (杠杆率、局部性与测试)

  • Leverage (杠杆率)：单次数据跨 CGO 传输耗时降低 65%~80%，GC 内存分配削减 60% 以上；
  • Locality (局部性)：所有类型映射与内存直传内聚于 Codec 单一接缝，业务 TS 与底层 Process 无感知；
  • Testability (测试性)：建立涵盖大整型、Map、多维切片与二进制 Buffer 的确定性单元测试套件。

03

全链路可取消 Context 穿透与执行管道 (End-to-End Context Pipeline & Execution Seam)

gou/api/handler.go · gou/process/process.go · gou/runtime/v8/runner.go · xun/dbal/query/query.go

Strong (强烈推荐)

Problem (执行接缝断裂与资源悬挂雪崩)

当前系统在请求生命周期管理上存在严重的接缝断裂 (broken seam)：
1. 在 gou/process/process.go:L70 中，只要传入 Context，就走 Slow-Path 分配 channel 并启动 go func()。一旦请求超时或客户端取消，Execute() 虽退出，但内部的 go func() **根本无法停止，后台持续空跑**！
2. 底层 xun 的 SQL 执行（Get()、Exec()）**完全没有接入 `context.Context`**（全部为无超时的裸 `db.Query/Prepare`）！ 客户端一旦取消请求，后端数据库依然在疯狂计算慢 SQL，连接池无法回收，V8 线程被卡死，最终引发级联雪崩。

Solution (深化为深模块)

构建统一的 Execution Pipeline（深模块）： 将标准 Go context.Context 贯穿到底： Gin Gateway → process.Execute(ctx) → Runner → TS 内部 Process() → xun.QueryContext(ctx) / ExecContext(ctx)。 一旦上层 Context 取消或超时： 1. 底层数据库连接立即发出中断信号并归还连接池； 2. Runner 立即触发 V8 原生 iso.TerminateExecution() 强行截断卡死的 JS 循环； 3. 资源秒级回收到池中，彻底消灭悬挂协程与僵尸查询。

Benefits (杠杆率、局部性与测试)

  • Leverage (杠杆率)：高并发下异常请求的系统自愈与容灾能力提升数倍，彻底杜绝连接池耗尽死锁；
  • Locality (局部性)：请求生命周期严格由 Context 托管，消除各模块散落的定时器与硬编码超时；
  • Testability (测试性)：通过单测注入超短超时（如 50ms），可精确验证从 HTTP 到数据库的即时熔断与资源释放。

04

Xun DBAL 写操作无 Prepare 直连与列式扫描器 (Direct Query Execution & Column Streaming Scanner)

xun/dbal/query/exec.go · xun/dbal/query/support.go · xun/dbal/query/query.go

Worth exploring (值得探索)

Problem (写操作 3x RTT 与单行 Map 堆内存碎片)

虽然此前在 query.go:Get 中移除了 SELECT 的 Prepare，但在 exec.go 中，**所有的写操作（INSERT、UPDATE、DELETE）仍然在每次调用执行 `db.Prepare(sql)`并在 defer 中 `stmt.Close()`**！ 在批量写入、日志归档与高频业务变更场景下，每一次写入依然承受 **3 次网络往返（3x RTT）** 与服务端句柄震荡。 同时，在 support.go:mapScan 中，每一行数据都分配一个独立的 make(xun.R, len(columns)) Map。拉取千条记录瞬时产生千个 Map 与数万次哈希分配，严重推高 GC 压力。

Solution (深化为深模块)

深化 QueryEngine： 1. 将写操作全面改造为直连执行：db.ExecContext(ctx, sql, bindings...)，彻底消除额外的 2 次网络往返； 2. 引入列式流式扫描器（Streaming Scanner），针对直接向外层序列化输出（如转为 JSON 或直通 V8 Codec）的场景，采用复用切片内存池，避免海量小 Map 的重复堆分配。

Benefits (杠杆率、局部性与测试)

  • Leverage (杠杆率)：数据库写吞吐提升 2~3 倍，数据库服务端句柄池压力降为零；大数据集查询内存分配减少 60%；
  • Locality (局部性)：底层驱动网络往返与扫描内存内聚于 DBAL，上层 Model 与业务 TS 零感知；
  • Testability (测试性)：可直接通过基准测试验证 0 Prepare 与低堆逃逸指标。

05

资产引擎阶段化并发加载与启动预热 (Concurrent DAG Asset Loader & Ahead-of-Time Pre-warm)

yao/asset/asset.go · yao/asset/discovery.go · yao/engine/load.go

Worth exploring (值得探索)

Problem (拓扑排序后的单协程串行瓶颈)

近期引入的统一资产引擎虽然支持了依赖拓扑排序，但在实际装载资产（discoverAndLoad）时，所有资产文件依然是**单协程纯串行装载**！ 系统在扫描数十甚至上百个 Model、API、Script 文件时，逐一进行磁盘 I/O、逐一解析 JSON/YAML。在多核现代服务器上，CPU 多核能力完全闲置，导致大型项目（如 syd/service）冷启动耗时长达数十秒。 且启动后未做 V8 Script 字节码与连接池预热，导致第一批真实请求遭遇冷启动延迟毛刺。

Solution (深化为深模块)

将资产加载器深化为 Concurrent DAG Stage Loader（深模块）： 根据依赖拓扑关系划分为阶段（Stages），同一阶段内无依赖的资产（独立 Models、Scripts、Connectors 等）使用受控并发池（如 errgroup.WithContext）多协程并行加载与校验； 在服务监听前，预热编译 V8 CodeCache 与数据库连接池，彻底消除首包抖动，将引擎整体冷启动时间压缩 70% 以上。

Benefits (杠杆率、局部性与测试)

  • Leverage (杠杆率)：复杂 Yao 应用启动提速 3~5 倍，首屏请求 P99 抖动消除；
  • Locality (局部性)：并发加载、依赖拓扑与错误聚合完全内聚在资产引擎，各 Loader 保持无状态；
  • Testability (测试性)：测试表面清晰，可单测验证高并发读取下的数据竞态（-race）与拓扑依赖顺序保证。

Top Recommendation (首要推荐)

建议首期攻坚：候选方案 01 (V8 上下文复用) 与 候选方案 02 (跨 CGO 二进制 Codec)

结合你们系统“以 TypeScript 为核心业务开发语言，高频穿透 Process 进行数据存取”的真实场景， 当前系统的最大性能杀手与高并发抖动根源是“每次脚本执行完毕后全量销毁重建 Context”， 第二大吞吐瓶颈是“Go 与 V8 之间仍在使用低效的 4 次 JSON 字符串编解码”。

优先攻坚方案 01 的战略原因：彻底抹平 P99 抖动与毛刺

改动局限在 gou/runtime/v8/runner.go 与 v8go 的 Handle 回收机制中，完全符合外科手术式重构（Surgical Changes）。一旦消除频繁销毁重建，避免触发 NumberOfNativeContexts > 200 的自毁逻辑，整个系统的请求延迟分布将呈现平滑的常数级稳定响应。

同步推进方案 02 的战略原因：释放核心数据通道吞吐

v8go 底层已经就绪了 codec.go 的二进制支撑。在 bridge 模块打通该接缝后，大结果集查询（如订单台账扫描）传回 TypeScript 的耗时将直降 70%，消除海量中间 JSON 字符串逃逸，GC 停顿与 CPU 占用大幅减轻。
