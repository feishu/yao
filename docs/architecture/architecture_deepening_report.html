Part 01 · 现状梳理

Yao 生态五大子项目的职责分工、数据流动与设计初衷。

1. yao (宿主与编排)

全能应用引擎二进制入口，统筹全局生命周期。

3. xun (数据库抽象层)

多数据库方言抹平与链式 SQL 构造。

  • MapStrAny 与 Dot/UnDot 扁平化

Part 02 · 架构摩擦剖析

当前架构的核心问题与设计缺陷 (Architectural Friction)

运用深浅模块与接缝理论，直击引发崩溃、内存暴涨与 P99 尖刺的根源。

1. QueryStack 是典型的浅层伪聚合 (Shallow Aggregator) Deletion Test 命中

QueryStack 暴露了庞大的对外接口（Builders, Params, Current, Push, Next...），但其内部并无高深抽象，只是一个用脆弱切片下标传递上下文的过程式流水账。它强制把 SQL 构建、字段过滤映射与关联结果拼接混杂在一起，导致关系图 traversal 毫无隔离性。
Deletion Test 结论：删除 QueryStack，将其拆解为专职的 RelationPlanner 与直连执行器，代码的复杂度将大幅**聚拢（Concentrates）**并获得坚固的局部性。

2. 数据库事务抽象（Transaction Seam）完全真空 高可用与一致性杀手

虽然 gou/model/atomic.go 名为 atomic，但底层完全没有真正的事务生命周期封装！所有写入均以 Autocommit 模式提交。若业务在一个复杂流中包含“创建订单 + 扣减库存 + 增加流水”，一旦中途发生网络波动或脚本异常，已执行的 SQL 无法回滚，直接导致灾难性的脏数据。**缺乏事务接缝，系统的高可用与容灾恢复完全无法立足**。

3. 全局裸 Map 与脱轨协程导致泄漏接缝 (Leaky Seams) 并发崩溃风险

gou/process.Handlers 是一个没有读写锁保护的全局裸 Map，动态加载时会直接引发 Go 致命错误 fatal error: concurrent map writes；Execute() 内部无条件启动 go func()，在超时提前返回后，孤儿协程脱轨逃逸继续向命名变量写入，造成严重数据竞态。

4. V8 运行时隔离机制过于粗暴，引发 CPU 与内存毛刺 P99 延迟元凶

为了避免全局变量污染，每次执行完强制 ctx.Close() 并在归还前调用 NewContext() 全新重建；且每次执行均调用 CompileUnboundScript 重新解析编译全量 JS/TS 源码。这导致单次调用产生高达 20~50ms 的纯编译与跨界 CGO 损耗，极度刺激 Go 堆分配器与 V8 GC。

Part 03 · 深模块演进路线

深模块重构候选方案 (Deepening Opportunities)

通过构建高杠杆、强局部性的深模块，彻底替换浅模块与修复泄漏接缝。

CANDIDATE 01 Recommendation: Strong

V8 运行时引擎：从“浅状态机与重复重构”进化为“预编译与沙箱隔离深模块”

Files: gou/runtime/v8/{runner,isolate,dispatcher}.go
浅模块症结 (Shallow Friction)

Runner 暴露过多内部细节（status, signal, destroyed, keepalive），但对真正的核心问题——“重复编译 CPU 浪费”和“Context 销毁重建震荡”毫无遮蔽。外部必须小心配合其状态机流转。

深模块重构 (Deep Solution)

构建深模块 ScriptEngine，对外提供单一高杠杆契约：Execute(ctx, scriptID, method, args) (Value, error)。 内部隐藏：全局 UnboundScript 字节码预编译缓存、基于单 Isolate 的清洁全局作用域重置（无需重复 NewContext）、以及通过 isolate.TerminateExecution() 强绑定的确定性取消接缝。

CANDIDATE 02 Recommendation: Strong

ORM 与关联管线：删除浅层 QueryStack，构建事务与直连执行深模块

Files: xun/dbal/query/{query,exec,support}.go, gou/model/stack.go
浅模块症结 (Shallow Friction)

1. 每次 Get() 强制调用 db.Prepare() 与 defer stmt.Close()，单次查询额外消耗 2 次网络往返（3x RTT）；
2. QueryStack.runHasMany 采用单层扁平 LIMIT 100，在多主记录批量预加载时导致后半段数据静默丢弃；
3. 完全缺乏数据库事务生命周期管理。

深模块重构 (Deep Solution)

彻底实施 **Deletion Test**：删除浅层 QueryStack，沉淀深模块 DataPipeline 与 TxManager。
内部隐藏：连接池直连执行与自适应 LRU Prepared Statement 缓存池、零反射原生指针行扫描、多父级内存 Hash 关联无损装配、以及标准化事务接缝 WithTx(ctx, func(tx) error)。

CANDIDATE 03 Recommendation: Strong

进程调度总线：消除裸 Map 与伪并发，重塑为无锁受控深模块

Files: gou/process/process.go
浅模块症结 (Shallow Friction)

process.go 是典型的职责弥散模块。暴露裸 Map Handlers 导致并发读写崩溃；每次调用通过多次 strings.Split 和 strings.ToLower 解析前缀；所有 Execute() 盲目启动独立协程，超时后孤儿协程泄漏污染。

深模块重构 (Deep Solution)

重构为深模块 ProcessRouter，对外暴露统一契约：Dispatch(ctx, name, args...) (Result, error)。
内部隐藏：采用 Copy-On-Write（写时复制）不可变字典，运行期完全零锁并发读；前缀路由 Radix 树缓存；同步 Process 就地当前协程执行，异步 Process 接入受控 WorkerPool。

CANDIDATE 04 Recommendation: Worth exploring

云原生生命周期监管器：从“粗暴停机”演进为“高可用监管深模块”

Files: yao/service/service.go, yao/engine/load.go, gou/server/http/http.go
浅模块症结 (Shallow Friction)

服务停机直接调用底层 srv.Close()，强行切断客户端 TCP 连接，在容器滚动更新时造成大量 502 Bad Gateway；写死 5 秒超时影响长流式 AI 接口；engine.Load 串行加载并吞没关键数据库错误。

深模块重构 (Deep Solution)

创建面向容器云原生高可用（HA）的深模块 Supervisor。
内部隐藏：K8s 优雅停机控制器（先置 `/readyz` 为 503 摘除流量，再通过 srv.Shutdown(ctx) 平滑排空在途请求）；DAG 依赖拓扑并发初始化；深度健康探针（深度检测 DB/Redis/V8 连接池余量）。

Part 04 · 编译器与运行时基建

Go 1.23 升级至 Go 1.27 的可行性与 P99 压测收益

评估跨代升级对尾部延迟（Tail Latency）、垃圾回收暂停与内存分配器的直接改善。

Green Tea GC (Go 1.26+)

分代并发垃圾回收算法默认启用。Yao 运行 JS 脚本和 ORM 映射时产生大量短周期对象，Green Tea GC 能直接降低 **40%~70% 的 STW 停顿时间**，是抹平 P99 尖刺的最直接利器。

Size-Specialized Allocator (Go 1.27+)

针对 <80 字节的小对象（如 interface{} 包装、Map 节点、数值装箱）分配速度**提升 30%**，大幅减轻多核并发时的分配器锁争用。

Swiss Tables Map (Go 1.24+)

Go 运行时底层 Map 升级为 Swiss Tables 架构，降低哈希冲突开销，使 kun/maps 高频读取吞吐提升 20%~35%，且抗哈希碰撞退化能力显著提升。

升级兼容性检查单 (Risk Checklist)
  • v8go CGO 静态链接：验证 Xcode Command Line Tools / clang 在新链接器下的兼容性，确保信号中断与 CGO 栈切换正常。
  • encoding/json/v2 默认严格性：Go 1.27 默认拒绝重复 Key 并对非法 UTF-8 报错。排查历史 DSL 配置是否存在重复定义，可通过 GODEBUG=jsonv2=0 预留过渡通道。
  • 第三方依赖库版本约束解除：升级到 1.27 后，可将前期在 kun 中被迫降级的 OpenTelemetry 与 gRPC 恢复升级至最新版。
