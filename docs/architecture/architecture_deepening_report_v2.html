Architecture Vocabulary

严格遵循的标准架构词汇表

Ousterhout 软件设计哲学 · 识别浅模块与构建深模块
Deep Module (深模块)
极简接口隐蔽极大实现复杂度，提供极高的开发与运行杠杆。
Shallow Module (浅模块)
接口复杂度接近其实现本身，不仅没减轻心智负荷，反倒增加抽象层次。
Seam (接缝)
无需篡改内部即可改变或观测行为的契约点。接口即测试表面。
Locality (局部性)
因相同原因变化、共享生命周期的状态与代码集中在一处，杜绝泄漏。
Deletion Test (删除检验)
删除该模块是聚拢了复杂度还是转移了复杂度？若聚拢则证明原设计浅薄。
Leverage (杠杆率)
接口提供的威力对比调用它所需付出的认知与集成成本之比。
Adapter (适配器)
连接两个异构接口的转换器。“一个适配器是假设接缝，两个才是真实接缝”。

01

TS 脚本预编译与执行缓存 (Script Precompilation & Bytecode Cache)

gou/runtime/v8/script.go · gou/runtime/v8/runner.go · v8go/isolate.go

Strong (强烈推荐)

Problem (架构摩擦与浅模块缺陷)

Runner 是一个典型的浅模块 (shallow module)。在 runner._exec() 中，每次接收到执行指令，都直接调用：
iso.CompileUnboundScript(source, origin, ...)
这意味着每次 HTTP 请求或 TS 脚本调用，V8 都要从头重新做一次完整的词法解析、AST 抽象语法树构建与字节码编译！脚本加载、依赖拼接与执行编译割裂在不同地方，缺乏局部性 (locality)。

删除检验 (Deletion Test)：如果在 runner._exec 中删除单次编译逻辑，脚本编译的复杂度不会溢出到其他业务层，而是会集中聚拢到 Script 模块的加载与缓存生命周期中（"Yes, concentrates"），这正是深模块的特征。

Solution (深化为深模块)

深化 Script 模块，将其改造为自包含的预编译字节码仓库 (Bytecode Repository)。在应用启动资产加载或热重载时，一次性将 TS 转译生成的 JS 编译为全局唯一的 UnboundScript，并缓存 V8 Code Cache 字节码。 Runner 仅作为轻量级上下文宿主，执行时直接调用 unboundScript.Run(ctx)，彻底消除热路径上的编译 CPU 损耗。

Benefits (杠杆率、局部性与测试)

  • Leverage (杠杆率)：单次执行延迟降低 70%~90%，吞吐量实现 5~10 倍跃升；
  • Locality (局部性)：所有语法解析与编译错误被完全隔离在资产加载阶段，配合已有的 yao scripts --error，实现编译期防线，线上零偶发编译崩溃；
  • Testability (测试性)：测试表面从庞大的 Dispatcher/Runner 状态机缩减为纯净的 Script.Compile() 单元测试。

跨 CGO 边界数据编解码器 (Value Codec & Zero-Copy Bridge)

gou/runtime/v8/bridge/bridge.go · gou/runtime/v8/functions/process/process.go · v8go/codec.go

Strong (强烈推荐)

Problem (架构摩擦与类型截断陷阱)

当前 bridge 模块是一个极度浅薄的适配器 (shallow adapter)： 在将 Go 对象传给 JS 时，使用 jsoniter.Marshal 并在 V8 内部调用 v8go.JSONParse；反方向则在 V8 内 JSON.stringify，再在 Go 内 jsoniter.Unmarshal。 每次 TS 脚本调用 Process("models.user.Get")，查询返回的数据集均历经 4 次完整的 JSON 编解码与 CGO 跨界内存拷贝！

致命的类型截断缺陷：在 bridge.go:211 中，为规避 BigInt 的 JSON 兼容问题，代码将 Go 的 int64、uint64 强制强转为 int32(v)！导致所有毫秒时间戳（如 1789307032000）、雪花 ID、大整型主键在跨语言时发生静默溢出截断，产生诡异的负数和查不到记录问题。

Solution (深化为深模块)

将 v8go 中已新增的 codec.go（基于 V8 原生二进制序列化 ValueSerializer / DeserializeValue）深化为完整的 Value Codec 模块并全面接入 gou/runtime/v8/bridge。 实现 Go 数据结构与 V8 堆对象之间的高速二进制克隆穿透；建立严谨的类型契约，消除 int32 强转截断，保证 64 位大整数在安全范围内转为 JS Number，超限时无缝映射为原生 BigInt；打通 Uint8Array 零拷贝通道。

Benefits (杠杆率、局部性与测试)

  • Leverage (杠杆率)：单次数据跨界开销减少 65%，杜绝中间 JSON 字符串分配，消除 GC 内存毛刺；
  • Locality (局部性)：所有数据保真规则集中在 Codec 单一接缝，业务 TS 与底层 Process 无需感知类型强转细节；
  • Testability (测试性)：针对全类型边界（Int64/Uint64/Float/Buffer/Date）具备确定性的编解码单元测试套件。

03

全链路上下文与可取消执行管道 (End-to-End Context & Cancellation Seam)

yao/service/service.go · gou/runtime/v8/script.go · gou/runtime/v8/runner.go · gou/runtime/v8/functions/process/process.go · xun/dbal/query/query.go

Strong (强烈推荐)

Problem (断裂的接缝与雪崩隐患)

当前系统在请求生命周期管理上存在严重的接缝断裂 (broken seam)：
1. 在 script.execPool 调用 runner.ExecInvocation 时，完全遗漏了传递 process.Context；
2. 导致 runner._exec 中调用 bridge.BindGoContext(ctx, inv.ctx) 传入了 nil；
3. TS 内部调用 Process("models.xxx.find") 时，bridge.GoContext() 恒为 nil，退化为无 context 的同步调用；
4. 底层 xun 的 SQL 执行更是完全没有 context 概念（全部为无超时的裸 db.Prepare/Query）。

高并发雪崩根因：当客户端主动断开网络或网关超时触发取消，整个后端的 TS 引擎、Process 调用以及 MySQL 查询完全无法感知取消！V8 线程被卡死的慢查询牢牢占用，Runner 无法归还池中，Dispatcher 产生级联超时，最终全站接口瘫痪。

Solution (深化为深模块)

构建统一的全链路执行管道 (Execution Context Pipeline)： 将 Go 标准 context.Context 贯穿到底： Gin Request → Process → Runner → TS 内部 Process() → xun.QueryContext。 在 Runner 内部启动 context 监听，一旦顶层取消，立即调用 V8 原生 iso.TerminateExecution() 强行中断脚本执行，同时底层数据库连接驱动立即向数据库发送中断信号并释放连接。

Benefits (杠杆率、局部性与测试)

  • Locality (局部性)：超时与取消的生命周期逻辑严格绑定于上下文，杜绝“孤儿查询”与“僵尸 Runner”；
  • Leverage (杠杆率)：用标准 Go Context 统一了 HTTP、Task、Schedule、脚本与数据库的协同停机，高并发韧性极大增强；
  • Testability (测试性)：可通过标准单测注入任意 context.WithTimeout(50*time.Millisecond)，确定性验证全链路即时熔断。

Xun DBAL 语句池化与反射消除 (Query Engine & Direct Row Scanner)

xun/dbal/query/query.go · xun/dbal/query/exec.go · xun/dbal/query/support.go

Worth exploring (值得探索)

Problem (浅抽象带来的 3x 网络往返与反射损耗)

xun/dbal/query 中的 Get() 与 Exec() 在每次查询时都执行： stmt, err := db.Prepare(...)，并在紧接着的 defer 中 stmt.Close()。 在跨机房或 LAN 网络下，一次简单的 SELECT 产生了 3 次网络往返 (COM_STMT_PREPARE + COM_STMT_EXECUTE + COM_STMT_CLOSE)，严重放大了 TS 数据查询的端到端延迟。 同时，support.go:359 逐列使用反射解析值，每次千条数据列表查询产生数万次反射和堆逃逸。

Solution (深化为深模块)

深化 QueryEngine： 日常查询直接使用 Go 原生驱动的 db.QueryContext(ctx, sql, bindings...)，消除多余的两次网络往返； 对高频固定查询模板引入 LRU Prepared Statement 缓存池； 在行结果扫描中，将列值解析替换为静态类型断言（直接判断 *interface{} 与 []byte），消除全反射调用。

Benefits (杠杆率、局部性与测试)

  • Leverage (杠杆率)：数据库读写延迟降低 40%~60%，极大减轻高并发下 MySQL 服务端句柄池压力；
  • Locality (局部性)：连接池生命周期与驱动优化内聚于 DBAL，上层 Model 与 TS 业务无感知获益；
  • Testability (测试性)：通过标准化 Mock DB 可直接验证语句复用率与零反射基准测试。

V8 上下文重置与轻量隔离 (Context Scope Recycle vs Destroy/Recreate Churn)

gou/runtime/v8/runner.go · gou/runtime/v8/dispatcher.go · v8go/context.go

Worth exploring (值得探索)

Problem (粗暴的状态隔离导致高频 Context 碎片)

在 runner.reset() 中，为了隔离请求间的 JS 全局状态，代码在每次执行后粗暴执行： ctx.Close()，并紧接着调用 v8go.NewContext(iso, tmpl) 重建全新 Context。 Context 是 V8 中的重量级结构（涵盖内置原型对象、安全作用域等）。频繁创建销毁导致 V8 Native Contexts 数量激增，迫使代码加入了 NumberOfNativeContexts > 200 时直接销毁 Runner 的权宜之计，引发规律性的 P99 延迟抖动。

Solution (深化为深模块)

借助近期在 v8go 中新增的 ResetRetainedValues() 与内部 Context 机制，深化为 Context Scope Manager。 在单次执行完毕后，仅清理挂载在 Global 上的请求级变量（如 __yao_data、console），并释放该次执行追踪的 Persistent 句柄，实现 Context 的纳秒级重置复用，消除整套 Context 的频繁销毁。

Benefits (杠杆率、局部性与测试)

  • Leverage (杠杆率)：Runner 归还与借出开销降低 90%，消除 Context 创建过程中的堆内存碎片；
  • Locality (局部性)：Isolate 实例在其生命周期内保持稳定的 Context 拓扑，消灭 Dispatcher 健康检查里的“超过 200 强制销毁”补丁代码。

Top Recommendation (首要推荐)

建议首期攻坚：候选方案 01 (脚本预编译) 与 候选方案 02 (跨 CGO Value Codec)

根据你们团队“业务大部分使用 TS 编写，高度依赖 Yao 内部 v8go、gou、xun”的实际定位， 系统当前的第一大性能杀手是“每次调用全量重新编译 TS 脚本”， 第二大稳定性与性能陷阱是“Go 与 JS 之间低效的 4 次 JSON 往返以及强制 int32 导致的截断隐患”。

先做方案 01 的战略原因：极高杠杆率

改动局限在 gou/runtime/v8 的 Script 与 Runner，完全符合外科手术式重构（Surgical Changes）原则，无需改动上层业务 TS 代码。一经落地，全量 TS 接口吞吐量可直接提升 5~10 倍，瞬间抹平 V8 脚本相比原生 Go 的解析差距。

同步做方案 02 的战略原因：彻底排除生产硬伤

v8go 底层已经完成了 ValueSerializer 的 C++ 桥接支撑，只需在 bridge 层打通接缝。这不仅大幅提升 Model 数据查询传回 TS 的性能，更能彻底终结生产环境中毫秒级时间戳、雪花 ID 被截断为负数的隐蔽灾难。
